# A Worker is pinned to its Worktree by the Adapter's argv, and the prompt names it

Run `run-20260916-135110` lost a whole Ticket to a new failure mode: the Worker did the work well, but committed it to the Consumer's checkout, because process cwd was the only thing tying it to its Worktree and its CLI (opencode) re-roots linked worktrees to the git common dir — every command, including `git commit`, ran one directory over. Process cwd is therefore not an anchor. A Worker Adapter's argv may now reference the Worktree with a `{cwd}` placeholder, interpolated per spawn with the Worktree's absolute path — in `custom()`'s `args` and in the print-mode adapters' `extraArgs` alike, since the seam is identical — and a placeholder-shaped `{token}` that is not `{cwd}` is a config lie **Doctor** fails, because a typo would silently reproduce this exact escape. The **Worker** prompt names the **Worktree**'s absolute path and the **Ticket**'s **Branch** instead of saying "the Branch already checked out in this directory", which resolved, from the Worker's point of view, to the Consumer's checkout; prompt-level instruction is weak enforcement, but naming the target costs nothing and removes a discovery step one Worker aced by luck (`git worktree list`) and the very next one died on. Relying on cwd was rejected by the incident; exposing a Consumer-supplied spawn function was rejected because static argv is the Adapter contract. Enforcement is layered: the argv anchor is the fence, the named prompt is the signpost, and detection is ADR 0037. A first-party `opencode()` Adapter (still #120) would pass `--dir <worktree>` on its own; it does not need to wait for this placeholder.
