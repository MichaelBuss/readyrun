# Continuing a capped Run is a new Run with an explicit base

Hitting the cap ends a Run (ADR 0005), so continuing is a new Run with a new Run Branch whose base is named by `--base <commit-ish>` — typically the previous Run Branch's tip — and a Run that stopped on the cap names that command, so the Consumer is told how to carry on without being told what to do with the work. A cap exists so a Consumer can slice a Frontier it does not want to run in one sitting, which makes across-Run continuation the common path rather than an edge, and until now there was no product way onto it: the next Run cut from whatever HEAD happened to be, so a Consumer who had not manually checked out the previous Run Branch silently handed the next Worker a tree missing the blockers it depends on.

Resuming the *same* Run — the same ref, more Tickets — was rejected because it is the single long-lived integration branch ADR 0028 already turned down, wearing a resume label: the timestamped name records when a Run started rather than which invocation is appending to it, the clean-stop report's "Run complete" would become a lie a later invocation retracts, and a Run Branch a reviewer had already begun reading would mutate underneath them. Prompting at the cap was rejected on timing rather than on principle: Init may ask because the Consumer pressed enter a moment ago, whereas the cap is reached whenever the last Worker happens to finish, with nobody there — a question would hold the process open indefinitely waiting for someone who has, by the premise of an AFK harness, walked away, and would hang a CI runner outright; a yes that raised the cap would also defeat ADR 0005's whole purpose, since the cap bounds an unattended bill and a prompt you can keep answering is not a bound. The cap-versus-empty-Frontier distinction that motivated the prompt is already delivered as a statement by the clean-stop report (#98), which costs nothing and survives having no human present. A zero-argument `--continue` that picked the most recent local `readyrun/run-*` was rejected because a heuristic that picks wrong reproduces the exact failure this decision exists to prevent — a Worker on a tree missing its blockers — with ReadyRun's fingerprints on the choice instead of the Consumer's, and because it cannot express continuing from the Run before last, which happens as soon as Run Branches are reviewed out of order; `--from` was rejected as a second noun for a thing already named, since the base is the word the code and ADR 0033 already use. Treating `git checkout readyrun/run-<stamp>` followed by `run` as sufficient was rejected because it parks the Consumer on a `readyrun/` ref they will forget they are on, and a commit made there lands on a ref the next Run is about to cut from; reading the base without moving HEAD is strictly better, which is a fair sign it is the right shape rather than a convenience. Wrapping `run` in a Clack launcher offering a Run Branch to pick from was weighed and deferred to #108 rather than refused, because resume is genuinely a human-present moment but the action is one command, and a launcher that pre-validated flag combinations would hold Doctor's knowledge in a second place. Failing Doctor when the base does not contain a blocker's landed work was left to #70: config is not lying about the Frontier here, so ADR 0009 does not reach it, and detecting it needs a walk of the Frontier's blockers against first-parent history — while starting fresh from the default branch after reviewing a Run Branch is a legitimate thing to have meant, which is why base facts are disclosed and not gated.

## Consequences

- ADR 0033 is narrowed rather than overturned: a Run still recommends no push and no merge, because integration is not its to own, but it does name its own next invocation, since declining to own integration is not the same as declining to explain how to run the tool again.
- A Run's base is no longer necessarily the Consumer's checkout, so anything that reads HEAD as the base is now reading a default rather than the answer.
- Continuing repeatedly leaves a chain of Run Branches, each containing the one before it. Accepted: the newest holds everything and the earlier refs are prefixes of it, which is cheaper than collapsing the distinction between a Run and a session that can be paused.
- Uncommitted work in the primary checkout still reaches no Worktree and the existing warning stays correct, because `--base` resolves a ref and never reads the working tree — so continuing does not require the checkout to have been clean.
- Revisit if choosing a base other than the newest Run Branch turns out to be common, which is the evidence #108 waits on.
