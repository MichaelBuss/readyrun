# Publishing stays informational until someone bumps, then merge publishes

Publishing on every push to `main` was fine; failing a PR because the version wasn't bumped was not — it punished PRs that had no reason to ship yet. `.github/workflows/ci.yml` now only runs `test` and `publish-preview` on `pull_request`; the latter only comments (never fails) on whether this PR's published-file changes are already shipped, ready to ship, or waiting on a bump — and mentions `/bump` even when there's nothing to ship yet, so it stays discoverable. Bumping happens on the PR itself via `.github/workflows/bump.yml`: commenting `/bump` (default patch) or `/bump minor` / `/bump major` on a PR runs `scripts/bump.ts` and pushes the version bump straight to that branch, so review and CI re-run against the real version that will ship. The branch's own `jsr.json` can be stale by then — another PR may have bumped and merged to `main` after this branch was cut — so the workflow reads `origin/main`'s version first and passes it as `--baseline`; `bump()` bumps from whichever is higher, the branch's own version or that baseline, instead of trusting a possibly-stale checkout. A `workflow_dispatch` button was tried as a second trigger, but it only exists at the repo's Actions tab with no link back to the PR — worse UX than the comment it was meant to complement, so it was dropped. `.github/workflows/publish.yml` runs on every push to `main` but checks `scripts/should-publish.ts` first and skips quietly if that version is already on JSR, so an unbumped merge is a no-op, not a failure. Bump and publish are separate workflow files from CI specifically so a PR's checks list only ever shows jobs that apply to a PR — no confusing "skipped" entries for jobs that only run on a comment or a push to `main`.
