# Publishing stays informational until someone bumps, then merge publishes

Publishing on every push to `main` was fine; failing a PR because the version wasn't bumped was not — it punished PRs that had no reason to ship yet. `.github/workflows/ci.yml` now only runs `test` and `publish-preview` on `pull_request`; the latter only comments (never fails) on whether this PR's published-file changes are already shipped, ready to ship, or waiting on a bump. Bumping happens on the PR itself via `.github/workflows/bump.yml`, triggered two ways into the same job: commenting `/bump` (default patch) or `/bump minor` / `/bump major` on a PR, or running "Bump version" manually from the Actions tab against that branch (`workflow_dispatch`, picking patch/minor/major from a dropdown) for anyone who prefers a button over typing a comment. Either path runs `scripts/bump.ts` and pushes the version bump straight to the target branch, so review and CI re-run against the real version that will ship. `.github/workflows/publish.yml` runs on every push to `main` but checks `scripts/should-publish.ts` first and skips quietly if that version is already on JSR, so an unbumped merge is a no-op, not a failure. Bump and publish are separate workflow files from CI specifically so a PR's checks list only ever shows jobs that apply to a PR — no confusing "skipped" entries for jobs that only run on a comment, a manual dispatch, or a push to `main`.
