# A Run Branch stays local, and the handoff is a report on stdout and on the Ticket

ReadyRun pushes nothing and opens no pull request: a Run delivers a local Run Branch plus an honest account of where the work is, and what becomes of it stays the Consumer's (ADR 0028). Because there is never a remote ref, there can be no pull request, so one-PR-per-Ticket versus per-Run versus a stack, and draft versus ready, are not decisions this product makes. The handoff that replaces them has two halves. On stdout, a Run ends with a completion report symmetric with the hard-stop report it already writes: Tickets landed, whether the Run Branch ref exists, the base it was cut from, and why the Run stopped — Frontier empty or cap hit, which is the only one of those facts git cannot recover afterwards. That report says where the work is and how to inspect it, and deliberately prescribes no push and no merge, because ReadyRun cannot both decline to own integration and recommend a workflow for it. On the Tracker, `leaveFrontier` names the Run Branch and the merge commit on the Ticket, on both Trackers — Linear gains a comment via `commentCreate` alongside its In Review transition, which it does not use today — and states that the ref is local to the machine that ran the Run, because a Ticket naming an unfetchable ref as though it were a shared location is the silent lie ADR 0009 and ADR 0029 exist to refuse.

Pushing the Run Branch was rejected on two grounds. The human cost it would delete is one command, unlike the ten hand-merges that justified ADR 0028, so the asymmetry that made that decision obviously right does not hold here. More importantly it would make ReadyRun a writer to shared infrastructure, a new class of authority backed by credentials nobody owns in this model — the harness owns Tracker auth and the coding CLI owns its own login, and push credentials would be a third, unassigned thing — firing CI, notifications and branch-protection rules as a side effect of an unattended loop. Pushing after each merge rather than once at the end was rejected for the same reasons at higher frequency, and a config knob was rejected under ADR 0025's standing rule against building a surface for a workflow no Consumer has yet. Letting the Consumer name the Run Branch was rejected because the timestamped name is what keeps Runs self-sorting and collision-free, and because ADR 0004 already keeps ref naming with the harness rather than with an author. A durable `.readyrun/last-run.md` report was rejected because everything durable it would hold is already in git — the branch list, the first-parent log whose merge messages ADR 0028 derives from the Ticket, and `git worktree list` — leaving only the stop reason, which is one line of the stdout report; the file it was modelled on, Ralph's `progress.md`, was loop memory injected into each iteration's prompt rather than a human handoff, and the Tracker and the Run Branch already fill that role here.

## Consequences

- `leaveFrontier(ticket)` must carry the landing it is reporting, which widens an interface published through `createTrackerAdapter` (ADR 0025). Free before 1.0, a breaking change after it.
- `leaveFrontier` must be called after the merge rather than before it, because the merge commit does not exist at the point `run` calls it today. That reordering also closes an existing window in which a merge failure leaves a Ticket off the Frontier with nothing landed — the Worktree must still be removed before the merge, since a Branch cannot be deleted while a Worktree has it checked out.
- A third party reading the Ticket cannot fetch the ref it names. Accepted: the operator who ran the Run is sitting at the machine that has it, and the comment says so rather than implying otherwise.
- Review happens on a local Run Branch, which settles the fork that #2, #92 and #93 were each parked on.
- Revisit if a Consumer ever runs ReadyRun somewhere disposable, such as CI, where a local ref dies with the container. That is the one scenario in which no-push fails rather than merely inconveniences.
